## 二、各步做法与技术要点

### 1. 测试集构建

| 项目 | 内容 |
|------|------|
| 文件 | `tests/qa_dataset.json` |
| 规模 | 30 个 QA pairs |
| 字段 | `id`, `question`, `answer`, `relevant_doc_ids`, `category`, `difficulty` |
| 覆盖范围 | bm.md 第 3-101 条（密级、定密、载体、密品、设备、要害部门、会议、人员、脱密期、法律责任） |
| 难度分布 | 简单 7 题、中等 15 题、困难 8 题 |
| 类型分布 | 事实型 25 题、概念型 5 题 |

**技术要点：**
- 每题标注 `relevant_doc_ids`（对应文档条目号），作为检索评估的 ground truth
- 覆盖多种查询模式：直接引用、条件判断、否定句式、短查询、法律术语

### 2. 文档摄入管线（ingest.py）

| 项目 | 内容 |
|------|------|
| 分块方式 | 按条目号正则解析 `\*?\d+\.` |
| 文档数 | 105 个 chunk |
| 元数据 | `doc_id`（条目编号）、`source`（文件名） |
| 存储 | ChromaDB PersistentClient |

**技术要点：**
- 正则 `r'\*?\s*(\d+)\.\s'` 兼容 `* 1.` 和 `4.` 两种格式
- `encoding='utf-8-sig'` 自动去除 BOM 标记
- 每个 chunk 携带 `doc_id`，用于评估时与 `relevant_doc_ids` 对比

### 3. 检索评估指标

| 指标 | 公式 | 含义 |
|------|------|------|
| Recall@K | 命中数 / 应命中数 | Top-K 中包含正确文档的比例 |
| MRR | 1 / 第一个命中位置 | 第一个正确文档的排名倒数 |
| NDCG@K | DCG / IDCG | 考虑排名位置的归一化增益 |

**NDCG 计算示例：**
```
检索结果: [5, 3, 10, 27, 50]，相关文档: [3, 4]

DCG  = 0/log2(2) + 1/log2(3) + 0 + 0 + 0 = 0.63
IDCG = 1/log2(2) + 1/log2(3) = 1.63       （理想排序）
NDCG = 0.63 / 1.63 = 0.39
```

### 4. 生成评估（LLM-as-Judge）

| 指标 | 评估内容 | 方法 |
|------|---------|------|
| Faithfulness（忠实度） | 回答是否基于检索内容 | LLM 对比检索片段与回答 |
| Answer Relevancy（相关性） | 回答是否切题 | LLM 对比问题与回答 |

**技术要点：**
- 采用 Chain-of-Thought（先推理后打分）
- 0-10 分制（5 个区间：0/3/6/9/10），避免分数聚集
- 分数解析从容错性考虑，从最后一行提取数字

### 5. BM25 稀疏检索（新增）

| 项目 | 内容 |
|------|------|
| 依赖库 | `rank_bm25` + `jieba` |
| 分词 | jieba 中文分词 |
| 索引构建 | 容器启动时从 ChromaDB 加载所有文档自动构建 |
| 原理 | TF-IDF 变体，精确匹配关键词 |

**技术要点：**
- BM25 擅长精确关键词匹配，弥补向量检索对短查询、术语查询的不足
- 索引在模块加载时一次性构建，后续查询无需重建

### 6. RRF 混合检索融合（新增）

```
RRF 公式: score(d) = Σ 1/(k + rank_i(d))

其中:
  k = 60（常数，平滑排名差异）
  rank_i(d) = 文档 d 在第 i 路检索中的排名（从 0 开始）
```

**融合流程：**
1. 向量检索返回 Top-5，每个文档获得 `dense_rank`
2. BM25 检索返回 Top-5，每个文档获得 `sparse_rank`
3. 对每个文档计算 RRF 融合分数
4. 按融合分数排序，取 Top-5

**技术要点：**
- RRF 无需归一化分数，直接用排名融合，实现简单且效果好
- k=60 是业界常用值，平衡头部和尾部文档的权重

| 忠实度 | 0.959 | - | - |
| 相关性 | 0.977 | - | - |

## 四、问题总结

### 4.1 已解决的问题

| 问题 | 原因 | 解决方案 | 效果 |
|------|------|---------|------|
| Q15 "什么是密品？" 检索失败 | 查询太短（2字），向量语义信息不足 | BM25 精确匹配"密品"关键词 | Recall 0→1.0 |
| Q30 "刑法如何处罚？" 检索失败 | 法律术语，向量模型未学到"处罚"≈"刑罚" | BM25 关键词匹配 | Recall 0→1.0 |
| Q26 "拟公开信息" 部分命中 | 向量检索只召回 1/2 相关文档 | BM25 补充召回另一篇 | Recall 0.5→1.0 |
| 多题排序不佳（MRR 低） | 向量检索的排序质量有限 | RRF 融合双路排名，提升排序 | MRR 0.762→0.873 |

### 4.2 遗留问题

| 问题 | 原因 | 拟解决方案 |
|------|------|-----------|
| Q2 "哪些事项不得确定为国家秘密？" 仍失败 | jieba 对"不得确定"分词不佳，BM25 也未命中 | 查询改写（LLM 将否定句转为关键词） |
| 检索耗时增加 183ms | 双路检索 + RRF 融合开销 | 可接受，若需优化可缓存 BM25 结果 |

### 4.3 后续优化方向

| 方向 | 预期收益 | 优先级 |
|------|---------|--------|
| 查询改写（LLM） | 解决 Q2 否定句问题，Recall→0.97+ | P1 |
| 多轮对话上下文 | 支持追问，提升用户体验 | P2 |
| Prompt 工程 + 引用溯源 | 回答标注来源，提升可信度 | P1 |
| 前端引用展示 | 视觉呈现检索来源 | P2 |

## 五、技术栈总结

| 组件 | 技术 | 版本/配置 |
|------|------|----------|
| 向量数据库 | ChromaDB | PersistentClient |
| Embedding 模型 | text2vec-base-chinese | 中文语义向量 |
| 重排序模型 | mmarco-mMiniLmv2-L12-H384-v1 | CrossEncoder |
| 稀疏检索 | rank_bm25 + jieba | BM25Okapi |
| 融合算法 | RRF (Reciprocal Rank Fusion) | k=60 |
| LLM | DeepSeek Chat | 生成 + 评估 |
| 评估方法 | LLM-as-Judge | CoT + 0-10 分制 |
| Web 框架 | Flask + Gunicorn | 2 workers × 4 threads |
| 部署 | Docker | 前后端容器化 |
